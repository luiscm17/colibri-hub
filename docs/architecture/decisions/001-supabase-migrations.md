# ADR-001: Supabase CLI for Database Migrations

## Status

Active

## Context

The Colibri Hub system uses Supabase as its database platform (PostgreSQL managed through Supabase). Schema changes need a reliable, repeatable migration mechanism that integrates with the platform's tooling and deployment model.

The project requires:

- Forward-only migrations with timestamped ordering
- Local development parity with remote environments
- Integration with Supabase's local development stack (Docker-based)
- Simple CLI workflow for generating and applying migrations

## Decision

We will use the Supabase CLI migration system exclusively for all database schema changes. Migrations live under `supabase/migrations/` as timestamped SQL files generated by `supabase migration new`.

Migration workflow:

1. Generate: `pnpm supabase migration new <name>`
2. Write imperative SQL in the generated file
3. Apply locally: `pnpm supabase db reset --local --no-seed`
4. Deploy: migrations are applied automatically on `supabase db push` or through CI

## Alternatives Considered

| Alternative | Pros | Cons | Reason Rejected |
|-------------|------|------|-----------------|
| Alembic (SQLAlchemy) | Python-native, auto-generate from models, familiar to Python teams | Requires maintaining ORM model parity, adds a migration tool orthogonal to the hosting platform, dual migration state tracking | Not aligned with Supabase platform — Supabase CLI already manages migration state, remote deployment, and local reset. Running both creates conflicting migration histories. |

## Consequences

**Positive:**

- Single source of truth for migration state (Supabase remote migration history)
- Local development uses the same migration path as production
- No ORM model drift — migrations are imperative SQL, always authoritative
- Supabase dashboard and CLI tooling work without configuration

**Negative:**

- No auto-generation from Python models — schema changes require manual SQL
- Developers must know SQL DDL (acceptable for this team)

**Neutral:**

- SQLAlchemy ORM mappings are declarative mirrors of the migration state, not generators of it
