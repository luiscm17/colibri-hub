# Finished Product (PT) Management — Normative PRD

> **Authority:** This is the single normative source for finished-product management business rules within Warehouse.
> Technical specifications derive from this PRD and may not redefine business rules documented here.

---

## 1. Business Scope

This PRD defines the business rules for **finished product (PT) management** within the Warehouse context of Colibri Hub:

- **Reception** of finished product from Operations.
- **Classification** of PT availability for distribution.
- **Dispatch** (sales and transfers) of PT from Warehouse custody.
- **Returns** of PT that had previously left Warehouse.

Finished product management handles PT from the moment Operations delivers it back to Warehouse through its eventual dispatch to clients or Marketing/Sales. The production identity under which PT returns is defined separately (see Production Identity PRD).

### Relationship to Other Capabilities

| Capability | Relationship |
|---|---|
| Production Identity | PT returns under the identity defined there; Warehouse does not redefine it |
| Bale Management | Separate capability; raw material lifecycle does not overlap with PT |
| Lot Processing (Operations) | Upstream; delivers PT to Warehouse and owns production quality data |
| Supplies | No direct relationship |

---

## 2. Problem Statement

When Operations completes production, the finished product returns to Warehouse custody for storage, classification, and eventual dispatch. The business needs:

1. A controlled acceptance process that validates PT delivery from Operations.
2. Visibility into PT availability and condition for distribution decisions.
3. A traceable dispatch process for sales and transfers (with change history when edits occur).
4. Traceability for returns of product that had already left Warehouse.

Without these capabilities, Warehouse cannot manage PT inventory, fulfill client orders, or maintain traceability.

## 4. PT Reception from Operations

### 4.1 Business Act

Reception is the acceptance of finished product back into Warehouse custody from Operations. It marks the return of the lot history to Warehouse.

### 4.2 Boundary Rules

1. Warehouse receives the lot under the **same identity** already used by Operations.
2. Warehouse does **not** recreate the production history — it accepts it.
3. Only **one reception** is permitted per production identity. A second reception for the same identity is not admitted.
4. The reception is the evidence of acceptance of the single Quality Send from Operations.
5. Until Warehouse registers the reception, the lot remains in pending validation status. A brief coordination note does not constitute acceptance.
6. The reception may use data inherited from Operations alongside Warehouse's own physical verification.

### 4.3 Data Inherited or Referenced from Operations

| Attribute | Source | Description |
|---|---|---|
| Production identifier (lot/production ID) | Operations | The identity defined by Warehouse and continued by Operations |
| Title | Operations | Production title |
| Color | Operations | Produced color |
| Client or destination | Operations | Target client |
| Quality state documented by Operations | Lot Processing | Read-only context; ownership remains with Lot Processing |
| Route-sheet facts (weight, bag count, unit count) | Inventario / Embolsado | Already recorded by Operations; Warehouse does not re-enter these |

### 4.4 Data Verified Locally by Warehouse

| Attribute | Description |
|---|---|
| Physical presentation received | How the PT is physically presented |
| Physical consistency of route-sheet facts | Warehouse verifies consistency of what Operations recorded |
| Visible incidents at reception | Differences or damage observed upon receipt |

> **Important:** Warehouse does not re-enter weight, bag count, or unit count. Those are facts already recorded by Operations in the route sheet. Warehouse reception records acceptance, physical presentation, and observed differences.

### 4.5 Data Generated by the Reception

| Attribute | Required | Description |
|---|---|---|
| Reception number | Yes | Unique identifier for this reception event |
| Business date of reception | Yes | Calendar date of acceptance |
| Responsible who receives | Yes | Warehouse actor accepting the PT |
| Supervisor or origin responsible | Yes | Operations actor delivering |
| Observations or differences detected | No | Free-text notes on discrepancies |

### 4.6 Technical Data (Automatic)

| Attribute | Source | Description |
|---|---|---|
| Registration timestamp | System | Date and time the record was created |

## 5. PT Availability Classification

### 5.1 Business Act

After reception, Warehouse decides how the PT is available for distribution — its operational disposition.

### 5.2 Boundary Rules

1. Classification occurs **after** PT reception.
2. It does **not** replace the quality assessment from Operations (which is owned by Lot Processing).
3. It defines how Warehouse will treat the PT for storage, reservation, or distribution.
4. Classification must **explicitly separate**: quality (Operations-owned), availability (Warehouse-owned), physical presentation, and operational destination.

### 5.3 Availability Catalog

| Status | Meaning |
|---|---|
| Disponible | Available for dispatch without conditions |
| Observado | Under observation; not immediately available |
| Disponible con condición | Available but with noted conditions |
| Defectuoso | Defective; terminal state within Warehouse |
| Entregado / Despachado | Already dispatched from Warehouse |

### 5.4 Functional Dimensions (Must Not Be Conflated)

| Dimension | Owner | Examples |
|---|---|---|
| Quality state | Lot Processing (read-only for Warehouse) | estándar / con nomenclatura / observado |
| Availability or disposition | Warehouse | disponible / observado / disponible con condición / defectuoso / entregado-despachado |
| Physical presentation | Warehouse | bolsa / suelto / otra presentación relevante |
| Operational modality or destination | Warehouse | industrial / ovillado / otra clasificación comercial u operativa |

### 5.5 Classification Data

| Attribute | Required | Description |
|---|---|---|
| Lot identity | Yes | The production identity of the PT |
| Business date of classification | Yes | Calendar date of the classification decision |
| Quality state (from Lot Processing) | Read-only context | Not persisted by Warehouse; read for context |
| Availability condition | Yes | Warehouse-defined operational disposition |
| Physical presentation | When applicable | Storage modality |
| Intended operational destination | When known | Planned destination for the PT |
| Warehouse observations | No | Free-text notes |
| Reason for change | When correcting | Justification if classification is revised |

### 5.6 Simplification Rules

- **Defectuoso** is a terminal state within Warehouse. It is not treated as waste. It does not normally return to available states.

## 7. PT Returns

### 7.1 Business Act

A return is the total or partial reentry of PT that had already been dispatched from Warehouse.

### 7.2 Boundary Rules

1. A return reintroduces stock into Warehouse custody.
2. It must maintain a reference to the original dispatch.
3. It does **not** create a new identity for the returned product.

### 7.3 Return Data

| Attribute | Required | Description |

## 8. States and Transitions

### 8.1 PT Lifecycle Within Warehouse

```text
Operations delivers PT
  → Reception (acceptance into Warehouse)
  → Classification (availability decision)
  → Dispatch (exit from Warehouse)
  → [optional] Return (reentry to Warehouse)
```

### 8.2 Transition Rules

| ID | Rule |
|---|---|
| PT-ST-01 | PT enters Warehouse only through a registered reception. |
| PT-ST-02 | Classification can only occur after reception. |
| PT-ST-03 | Dispatch can only occur for PT that has been classified as available. |
| PT-ST-04 | A return references a prior dispatch and reintroduces stock. |
| PT-ST-05 | Defective PT does not normally return to available states. |
| PT-ST-06 | Only one reception per production identity is permitted. |

---

## 9. Cross-Cutting Rules (Applicable)

1. **Business date vs system timestamp:** Each business act records a calendar date entered by the actor. The system registration timestamp is separate and automatic.
2. **Correction with audit:** If an error is made, the record may be corrected, but only with full audit trail.
3. **Operational window:** Corrections by operational roles are allowed within the policy-defined window. Outside that window, only SysAdmin may edit.
4. **Permissions are configurable:** Current actor assignments are not rigid.
5. **Domain write separation:** Warehouse writes PT reception, classification, dispatch, and return data. Operations writes production and quality data. Neither overwrites the other.

## 10. Acceptance Criteria

| ID | Criterion |
|---|---|
| AC-PT-01 | PT can be received from Operations in a single operation per production identity. |
| AC-PT-02 | A second reception for the same production identity is rejected. |
| AC-PT-03 | Reception records acceptance and physical observations without re-entering route-sheet data. |
| AC-PT-04 | Classification requires a prior reception. |
| AC-PT-05 | Dispatch requires the PT to be in an available classification state. |
| AC-PT-06 | Dispatch records type, quantity, destination, and authorization. |
| AC-PT-07 | Returns maintain reference to the original dispatch. |
| AC-PT-08 | Returns do not create a new production identity. |
| AC-PT-09 | All business dates accept calendar dates (no time component). |
| AC-PT-10 | All registration timestamps are system-generated. |
